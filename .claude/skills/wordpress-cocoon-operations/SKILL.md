# WordPress（Cocoon）サイトの技術セットアップ・運用

WordPress管理画面をユーザーのブラウザセッション越しに操作して、固定ページ・カテゴリー・メニュー・SEO・セキュリティ・解析などのサイト基盤を構築・変更するためのスキル。ここに書かれているハマりどころは、実際の作業で一度失敗して学んだものなので、同じ事故を繰り返さないために必ず目を通す。

## 基本の操作方法

ユーザーがブラウザで管理画面（`/wp-admin/`、Cocoonの場合はログインURLが変更されていることもある）にログインした状態を保ってもらい、Claudeはそのページから認証情報を得てWP REST APIを直接叩く、という分担で進める。

1. 管理画面の任意のページに埋め込まれている `wpApiSettings.nonce` をスクレイプする
2. REST APIへのリクエストには `X-WP-Nonce` ヘッダーとしてこの値を付ける
3. **例外: Site Kit by Google（GA4/Search Console連携プラグイン）のREST APIだけはヘッダーではなく `?_wpnonce=<nonce>` のクエリパラメータが必要**。ヘッダーだけ付けると403になり原因が分かりにくいので、Site Kit関連の操作で403が出たらまずこれを疑う

固定ページ作成・カテゴリー作成・メニュー編集など、REST APIで完結する作業はこの方法で進めてよい。

## 自動化できない操作

**プラグインやテーマのインストール操作は、自動化を検知するブロッカー（auto-mode classifier）に阻まれる。** これはClaude側の問題ではなくガードレールなので、回避しようとせず、素直にユーザー本人に「これは手動でお願いします」と伝えてインストールしてもらう。インストール後の設定作業（有効化後のオプション調整など）はREST API/DOM操作で続けられる。

## Cocoonテーマ設定を変更するときの注意（最重要）

Cocoonの設定画面（`admin.php?page=theme-settings`）は、約977フィールドが1枚のフォームに詰め込まれた巨大な設定画面になっている。ここを操作するとき、**fetchでフォームの値を再構築して送信するようなやり方はしない。** 送信されるはずの他のフィールドが欠落し、意図しない設定リセットを引き起こすリスクがある。

正しいやり方は、**表示されているページのライブDOM上で該当のチェックボックスやテキストフィールドを直接操作し、そのままページ内の「変更をまとめて保存」ボタンをクリックする**こと。フォーム全体を経由させることで、他のフィールドはそのまま維持される。

### カスタマイザーの追加CSSを変更する場合
追加CSSの設定IDは `custom_css[cocoon-master]`。カスタマイザーのJS APIを使って
```js
wp.customize('custom_css[cocoon-master]').set(/* CSS文字列 */)
```
としたあと、**必ず「公開」ボタンをクリックする**（setしただけでは保存されない）。

### 子テーマは安易に有効化しない
`cocoon-child-master` のような子テーマを有効化すると、環境によってはCocoon側の設定（SNSシェア設定・フォント設定など）が**全リセットされる事故が実際に起きた**。テーマのPHP/テンプレートファイルを直接編集する必要が生じない限り、追加CSS（カスタマイザー）＋Code Snippetsプラグインの組み合わせで親テーマのまま運用するのが安全。

どうしても子テーマへの移行が必要になった場合は、必ず次の順序を守る：
1. Cocoon設定のバックアップ機能で現在の設定をエクスポートする
2. 子テーマを有効化する
3. エクスポートした設定をインポートして復元する

## Code Snippetsプラグインでコードを設置するとき

カスタムPHPコードを埋め込む際、**コードを誤って「説明」欄に貼ってしまうと、コードとして認識されず動かない**というミスが実際に起きた。正しい手順は：

1. コードは必ず**「スニペットコンテンツ（コード）」欄**に貼る（「説明」欄ではない）
2. 実行場所は**「すべての場所で実行」**を選ぶ
3. 保存は**「Save Changes and Activate」**ボタンで行う（Activateしないと有効化されない）

設置後は、想定通りに動いているか検証する。例えば「未ログイン時にAPIエンドポイントを404にする」ようなコードなら、匿名アクセスで404になること・正規のログインユーザー（nonce付きリクエスト）では通常通り動くこと、の両方を確認する。片方だけ確認して終わらせない。

## セキュリティ強化の型

WordPressのセキュリティプラグイン（CloudSecure WP Security等）で対応する定番項目：
- ログイン失敗時のロックアウト
- エラーメッセージの統一（ユーザー名/パスワードどちらが違うか特定させない）
- `?author=N` によるユーザー名探索のブロック
- XML-RPCの無効化
- ログインURLの変更（デフォルトの `/wp-login.php` から別パスへ）
- シンプルなWAF（Web Application Firewall）の有効化

REST APIについても、未ログイン時に `/wp-json/wp/v2/users` のようなユーザー情報が見えるエンドポイントを404化し、oEmbedレスポンスから投稿者情報を除去しておくと、ユーザー名の推測によるログイン試行のリスクを減らせる（Code Snippetsで実装し、上記の手順で検証する）。

## 「記事量産前にやること」チェックリストを作る

ある程度サイトの土台（固定ページ・カテゴリー・メニュー・解析・セキュリティ）ができたら、記事を量産する前にやっておくべき細かい設定を、**手戻りの大きさ順**にチェックリストとしてまとめて渡す。これは「後から直すと影響範囲が大きいもの」を先に、「後回しにしてもコストが小さいもの」を後にする、という並び方が肝心（例：サイトマップの重複解消や管理者メールの変更は早めに、ファビコン設定のような見た目の調整は後でもよい）。

典型的なチェック項目の例：
- 管理者メールをサイト専用アドレスに変更したか
- サイトマップが複数出力されて重複していないか（テーマ側とプラグイン側で二重に出ることがある）
- コメント・ピンバックを既定オフにしたか
- ファビコン（サイトアイコン）を設定したか
- お問い合わせフォームの送信先を確認し、テスト送信を1通行ったか
- アイキャッチ画像のひな形を用意したか（→ `blog-eyecatch-image` スキール参照）

まとまった分量になるので、チェックリストはArtifact（またはMarkdownの表）として渡し、チャット本文に流し込みすぎない。

## 気をつけること

- REST APIで完結する作業と、手動でしかできない作業（プラグイン/テーマのインストール）を最初に切り分けて、後者はユーザーに早めに依頼する。作業の後半で「実はこれは手動でした」と気づくと手戻りになる。
- Cocoonの巨大設定フォームと子テーマの事故は、いずれも「一括で楽をしようとする」ことで起きた。急がば回れで、ライブDOM操作かバックアップ経由の移行を徹底する。
- セキュリティ設定を入れたら、必ず「意図通りブロックされるか」と「正規の利用が壊れていないか」の両方を検証する。

# ブラウザだけで動く小さなアプリの作り方

このリポジトリの2つのアプリ（`log/` と `wake/`）は同じ型で作られている。
3つ目以降も同じ型に乗せる。常に守る決まりは `CLAUDE.md` にあるので、
先にそちらを読んでからここに戻ってくること。

## なぜ手順を踏むのか

依頼は「こういうアプリが欲しい」という形で来る。そのまま額面どおりに作ると、
**要件をすべて満たしているのに使われないアプリ**ができる。ワケワケの例で言うと、
「タスクを分解して一覧・カレンダーで見る」という4つの要件をそのまま作れば、
階層ツリーが1枚目に出るアプリになる。だがコンセプトは「次の一手を早く実行する」
だった。ツリーが1枚目だと、木を眺めて満足して終わる。要件と正面から衝突している。

だから最初にやるのは、コードを書くことでも画面を並べることでもなく、
**コンセプトを「起動して1枚目に何が出るか」に翻訳すること**。

## 手順1 — コンセプトを1枚目に翻訳する

ユーザーが語ったコンセプトから、次の3つを言葉にする。ここを飛ばさない。

1. **このアプリで一番大事な一動作は何か**（記録する／次の一手を選ぶ／振り返る）
2. **その一動作の対象になる最小単位は何か**
   - ワケワケ … 葉タスク（それ以上分解されていない末端）＝いま実行できる単位
   - ログ … 1件の記録（期間・点・体調）
3. **1枚目にはその単位だけを並べる。** 構造（木・階層・分類）は編集用の別画面へ

要件に書かれていない画面を1つ足すことになる場合がある。それでいい。
足すときは、なぜ必要かをユーザーに説明して合意を取ること。

## 手順2 — 作る前に要件の抜けを埋める

「設計して」と言われたら、すぐ作らずに一度整理を返す。埋めるべき穴は毎回だいたい同じ。

| 決めること | 既存2アプリでの答え |
|---|---|
| 保存先 | localStorage（アプリごとにキーを分ける） |
| 端末間の同期 | しない。JSON の書き出し／復元が引き継ぎ手段 |
| 日付の粒度 | 用途しだい。締切なら日付のみで足りることが多い |
| 完了・集計の自動計算 | 自動を既定にし、手で上書きできるようにする |
| 通知 | ブラウザだけでは確実に出せない。`.ics` 書き出しが確実な代替 |
| 主に使う端末 | スマホ前提で作る |
| v1で削るもの | **明示的に決める。** 繰り返し・検索・タグ・添付は後回しにしやすい |

判断が分かれて作るものが変わる項目だけ聞く。推奨を添えて聞くと早い。
それ以外は推奨で進めて、あとから直せるようにしておく。

## 手順3 — 置き場所とファイル

フォルダを1つ作り、その中で完結させる。`.github/workflows/pages.yml` は触らない。

```
<アプリ名>/
  index.html              画面の骨格。<script> を並べるだけ
  css/style.css           ライト／ダーク自動
  js/store.js             データ層（localStorage・整合・取り消し）
  js/model.js             集計や導出（必要なら）
  js/ui.js                日付ユーティリティと共通UI部品
  js/<画面>.js            画面ごとに1ファイル
  js/app.js               画面の切り替えと設定
  manifest.webmanifest    id にそのアプリの公開パスを必ず書く
  sw.js                   Service Worker（このフォルダに置けばスコープが閉じる）
  icons/                  隣のアプリと見分けのつくもの
  README.md               そのアプリの説明（公開されない）
```

manifest には **`"id": "/<アプリ名>/"` を必ず書く。** 省くと `start_url` が
同一性の代わりになり、あとで置き場所を変えたときインストール済みのものが
別アプリ扱いになって開けなくなる（実際に起きた）。

アイコンは既存2つと並べて見分けがつくものにする。ログは青、ワケワケは緑。
`icons/` の生成は Python の Pillow で描ける（`wake/icons/` を作ったときの方法）。

## 手順4 — 実装の作法

コードの作法は `CLAUDE.md` に書いてある。それに加えて、既存2アプリで
効いている作り方を挙げる。

- **取り消せるようにする。** 破壊的な操作の前に状態のスナップショットを取り、
  トーストに「取り消す」を出す。木構造やまとめて完了のような、一発で
  取り返しがつかなくなる操作ほど効く
- **入力の速さを削らない。** 1行に1つ書いてまとめて追加する、
  「今日／明日／今週末」のワンタップなど。入力が遅いアプリは使われなくなる
- **自動で決まる値には「自動」と分かる見た目を与える**（破線のバッジなど）。
  そのうえで手で上書きできるようにする
- **データの整合はデータ層で保つ。** 木構造なら、変更のたびに親子関係を
  たどり直して、迷子や循環をその場で直す関数を1つ持つ（`wake/js/store.js` の
  `reindex`）。画面側で気をつける作りにしない
- 画面を切り替えたらスクロール位置を先頭に戻す
- タブのアイコンに絵文字や記号の文字を使わない。環境によって化ける。
  その場でインラインSVGを組む（`wake/js/app.js` の `icon`）

## 手順5 — 確かめる

**読み返すだけで終わらせない。実際に動かす。** この環境には Chromium が
入っていて Playwright から使える（`/opt/pw-browsers/chromium`）。

```js
const ctx = await browser.newContext({ ...devices['iPhone 13'] });
```

見るのは次の5つ。

1. **スマホサイズで実際に操作する。** 追加・編集・削除・画面の切り替えまで通して、
   `pageerror` と `console.error` が0であること
2. **公開手順を実際に流す。** ワークフローのコピー手順をそのまま実行して、
   出来上がる並びを確認する。ローカルで配信して各パスが 200 で返ることも見る
3. **`sw.js` のキャッシュ対象が全部実在すること。** 1つでも欠けると `addAll` が
   失敗し、オフラインが丸ごと無効になる。スクリプトで機械的に照合する
4. **オフライン。** Service Worker がページを支配してから
   （`navigator.serviceWorker.controller` を待つ）オフラインにして reload する。
   待たずにオフラインにすると、まだ支配していないので落ちて誤検知になる
5. **導出ロジックは個別に検証する。** 自動集計や木構造なら、境界と異常系を
   直接叩く（親を自分の子に付け替えても壊れないか、など）

## 落とし穴

「ログ」と「ワケワケ」で実際に踏んだもの。

- **manifest の `id` を省く** → 置き場所を変えた瞬間、インストール済みアプリが
  別物扱いになり、古い `start_url` を見に行って開けなくなる
- **ドメイン直下に Service Worker を置く** → スコープが下位を全部拾う。しかも
  一度登録されるとファイルを消しても更新に失敗して端末に居座り続ける。
  取り消すには「自分を unregister するだけの Service Worker」を同じURLに置くしかない
- **`sw.js` の ASSETS に実在しないファイルが1つ混じる** → `addAll` が失敗して
  オフラインが丸ごと効かなくなる。しかも画面上は普通に動くので気づきにくい
- **network-first で `{ cache: 'no-store' }` を書き忘れる** → ブラウザの通常の
  HTTPキャッシュから返り、「ネットワーク優先」のつもりで古い内容を掴み続ける
- **`cache.put` は 404 も保存する。** 2xx 以外も通るので、消えたURLを
  取りに行くと 404 で正常なキャッシュを上書きしてしまう
- **`position: sticky` の要素を縦に2つ並べる** → 上端で重なる。
  ひとかたまりに包んで、その外側だけを sticky にする
